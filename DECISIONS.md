| D-030 | Correction to V2's per-source token-validation rate limiter (D-018/plan.md §13.1): the client key was derived from `request.client.host`, the immediate TCP peer — behind the project's one same-origin reverse-proxy hop (local docker-compose nginx; Firebase Hosting's `/api/**` rewrite to Cloud Run in production, D-029), that collapses every real customer onto one shared value, making the "per-source" lockout global instead of per-customer (one attacker's lockout would deny every legitimate customer, not just themselves) — a violation of plan.md §13.1's own explicit acceptance requirement that the limiter "does not block legitimate customers." No spec/plan text changed — plan.md §13.1's own requirement was already correct; only the implementation was wrong. Human decided 2026-08-18 to fix immediately as an approved V2 correction rather than deferring. | Implemented — V3 Phase 13, DONE 2026-08-18 |
| D-031 | **Constitution Amendment 1.1.0 — first-ever amendment to Article III** (`.specify/memory/constitution.md`). | D-033 | Correction to feature 005's guided booking selection (GB), found through real use immediately after D-032 shipped. Two real defects: (1) embedding-similarity slot-choice matching (GB-2) cannot resolve ordinal/positional replies ("segunda opção", "3") — they share no semantic content with an offer's own specialty/day/time text, so no threshold fixes this; fixed with a deterministic ordinal/positional parser tried before embedding similarity. (2) The original design paused for a separate "Deseja que eu confirme o agendamento?" question (GB-4) before handing off to AA-10's autonomous script via an independently-typed booking-intent phrase — real use found this felt broken (a redundant reconfirmation, then no path forward without the customer separately typing something like "quero marcar"). Human decided 2026-08-19: once a slot's details (date/time/price) are stated, proceed directly to asking CPF, then payment, with no separate confirm/cancel gate — but keep this entirely inside N2 (one operator click per step, same decision already made for D-032), not by extending Constitution Amendment 1.1.0. Implemented as GB's own parallel CPF/payment conversation — reusing `booking_script.parsing`'s pure `extract_cpf`/`extract_payment_confirmation` (no DB, no I/O, no autonomous-send coupling; the one disclosed import from `booking_script/*`) to produce ordinary operator-approved drafts with AA-10's own message wording, never calling `send_scripted_message`/`advance_booking_script` and never touching `conversation.booking_script_step`. The raw CPF/payment reply is parsed synchronously at message-creation time (mirroring AA-10's own request-local-only principle, since the durable message is redacted immediately afterward) and only the already-computed, safe result text is staged transiently on the conversation for the next draft-generation call — the raw value itself is never persisted anywhere, extending AA-10's own non-retention rule to this parallel path. `booking_script/service.py` remains untouched; structural containment re-verified. | Implemented — feature 005 correction DONE 2026-08-19 |
| D-034 | Second correction to feature 005/GB, found through further real use immediately after D-033 shipped. Two real defects: (1) `latest_unconfirmed_offer_generation_id()` never recognized a booking as *finished* — after `GUIDED_BOOKING_COMPLETE`, the next customer message, even a wholly unrelated clinical question ("Em quanto tempo descubro se eu tenho câncer?"), kept matching the same stale offer set via embedding similarity instead of falling through to ordinary RAG/LLM composition; fixed by treating any `GUIDED_SLOT_SELECTION`/`GUIDED_CPF_CONFIRMED`/`GUIDED_BOOKING_COMPLETE` generation found after the offer-resolving one as proof the set is no longer pending. (2) A genuinely uncovered clinical question could still surface a technically-`ANSWER` but substantively wrong dynamic-pattern/LLM draft (e.g. an unrelated scheduling Q&A) instead of deflecting to a professional. Scoped outside the GB/scheduling flow and never applied against `full_parent_draft`'s own clinical-document match (an actually-matched clinical document is already the strongest available grounding). New audit event `ai.clinical_deflection_applied`. | Implemented — feature 005 correction DONE 2026-08-19 |
